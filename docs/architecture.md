# 框架与执行规则

GoalKeeper 核心是独立模型与工具循环，不用原生 Codex 执行解题，不强制拆阶段或调用子 Agent。原生产品适配器用于四组评测。

1. CLI 根据 Task 建立独立工作区、固定检查和截止时间。
2. context 保持目标和历史前缀稳定，把已送达的新要求追加到历史。工具调用和结果组成完整事务，不在事务中间压缩。
3. Engine 调用模型，工具先核对范围再执行。多个独立工具调用可以合并到一轮；实际执行按工具安全约束处理，不保证所有工具同时执行。
4. 根据实际输入校准上下文估算。需要压缩时保留近期正文，生成结构化摘要并核对来源；失败后最多一次纠正，避免无效摘要循环。归档按内容哈希保存。
5. 检查结果关联文件状态、命令、任务版本和环境。交付时必须通过当前规定检查，不能只依据模型声明。规定检查的完备性仍由任务定义决定。
6. Store 原子保存并核对序号，防止过期状态覆盖新记录。恢复检查未完成事务，不重复执行结果不确定的写入。
7. 计量保留主任务与摘要、输入输出、未知用量和时间。评测转发层可以有限重试临时请求，但不延长任务截止时间，也不自动重跑整题。

## 隔离与权限

模型工具只能访问 Task 授权的工作区与只读运行依赖，不能读账户或评分目录。命令使用 macOS Seatbelt。符号链接、路径逃逸、受保护检查和文件变化分别检查；停止后清理进程。认证由工具循环之外的 AuthBroker 处理，凭据存于系统钥匙串。

## 参数与状态

默认配置见 configs/default.json。目标、约束、验收、文件范围及规定检查由 Task 定义。State 保存历史、目标版本、已收到的要求、工具事务、检查证据和用量。CLI 必须在源码 checkout 中使用；当前 paths.py 不提供独立安装后的任意外部项目访问。

## 代码导航

- src/goalkeeper/engine.py：主循环、检查与交付。
- src/goalkeeper/context.py：输入、摘要、事务和来源校验。
- src/goalkeeper/tools.py、sandbox.py：操作与沙箱。
- src/goalkeeper/storage.py：检查点、归档和快照。
- src/goalkeeper/transport.py：四组共享模型转发与计量。
- src/goalkeeper/native.py、codex.py：原生对照接入。
- src/goalkeeper/readiness.py：真实评测前的离线身份与证据核对。
